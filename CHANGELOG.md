# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Osirion.Blazor.Core: `HeroSection` takes `Aside`, content of your own shown beside the copy instead of the side image, such as a sample record (`osirion-hero-aside`, and `osirion-hero-with-aside` on the section): on the right from 768px and below the copy on narrower screens. When `Aside` and `ImageUrl` are both set the aside wins, and neither the side image nor `FrameImage` is shown; a background image still shows and keeps one column. Without it the hero renders as before
- Osirion.Blazor.Cms.Domain, Osirion.Blazor.Cms.Infrastructure and Osirion.Blazor.Cms.Web: content blocks. A content item whose front matter has `blocks:` renders as a page composed of Osirion components, in the order of the list, instead of its Markdown body (`body: after` renders the body after them), so a site writes a landing or product page as Markdown instead of a Razor page. The types are `hero` (`HeroSection`), `section` (`OsirionBaseSection`), `steps` (`OsirionSteps`), `cards` (`OsirionFeatureCard` in a grid), `metrics` (`OsirionMetricGrid`), `faq` (`OsirionFaq`, with FAQPage structured data from the first `faq` block of a page), `cta` (`OsirionCallToActionSection`), `image`, `markdown` and `component` (a component the site registers by name); `split`, `checklist` and `record` are read and validated and render nothing, with a warning naming the type, until their components are in the library. `ContentBlockParser` reads them into typed records (`HeroBlock`, `StepsBlock` and the others, `CustomContentBlock` for a type the library does not define) on `ContentItem.Blocks` and `ContentItem.BodyPlacement`, and checks `type`, `id` (`[a-z0-9-]+`, unique), `variant`, `tone`, `columns`, `aside_position`, `body`, the required keys of each type, keys a type does not have, and links (a site path, a fragment, `https:`, `mailto:` or `tel:`; `javascript:`, `data:`, `http:` and `//host` are refused). A file whose blocks break a rule does not load, as a file with broken YAML does not, and the logged `ContentBlockException` names every problem with the file, the block index and the key. `OsirionContentBlocks` renders a list of blocks; `ContentRenderer` and `LandingPage` use it for an item with blocks, and an item without blocks renders as before. Text is plain or inline Markdown, `markdown` values and answers are block Markdown, and all of it goes through the registered `IHtmlContentSanitizer`; site paths are localized with `IOsirionLocalePaths` when it is registered. `AddOsirionContentBlocks` registers site renderers by type (`AddRenderer<TRenderer>`, deriving from `ContentBlockRenderer<TBlock>`), components by name (`AddComponent<TComponent>`) and a fallback renderer (`UseFallbackRenderer<TRenderer>`) in a `ContentBlockRegistry`; a block nothing can render logs an error and renders nothing, or a notice in Development. A derived locale transliterates the text of an item's blocks (`ContentBlockText.Map`), leaving identifiers, choices, addresses and component parameters as written. `SeoMetadataRenderer` leaves out its generated FAQPage for an item with a `faq` block. The new guide `/docs/content-blocks` describes every type and key
- Osirion.Blazor.Core: `OsirionFaq` takes `AnswerTemplate`, which renders each answer in place of the plain-text paragraph, for formatted answers; the structured data still uses `FaqItem.Answer`. Without it the component renders as before
- Osirion.Blazor.Core: `OsirionSplitSection` places copy (`Content`) beside an aside (`Aside`), such as an image or a sample record, in two equal columns from 768px, with the aside stacked under the copy below that. `AsidePosition` (`End` by default, or `Start`) moves only the aside's column, so the copy stays first in reading and keyboard order. It needs no script. The documentation site documents it at `/components/split-section` with a live demo
- Osirion.Blazor.Core: `OsirionRecordCard` frames a sample record, such as an order, a ticket or a decision, for a page that shows what a product produces: a `Title` at `HeadingLevel` (`3` by default), a `Status` badge whose `StatusTone` (`Neutral`, `Positive`, `Negative` or `Warning`) only colors it, so the status never rests on color alone, labelled `Rows` as a description list (`RecordCardRow` in `Osirion.Blazor.Core.Models`) and a `Footnote` such as "Sample data" as the `figcaption` of its `figure`. The tones use the `--osirion-status-*` tokens; with nothing to show it renders nothing. The documentation site documents it at `/components/record-card` with a live demo
- Osirion.Blazor.Core: `OsirionFeatureCard` takes an `Icon`, a decorative fragment above the title in an `aria-hidden` tile that, without an `ImageUrl`, takes the place of the image placeholder, so the card is one column as tall as its content (`osirion-feature-card-with-icon`), and `Items`, short phrases behind check marks rendered through `OsirionChecklist`. A card that sets neither renders the markup it rendered before
- Osirion.Blazor.Core: `OsirionCardGrid` lays cards out in equal columns: `Columns` (`1` to `4`, `3` by default; a value outside the range moves to the nearest one) from 992px, at most two from 640px and one below. The count is a class, not an inline style, so the grid writes no `style` attribute for a Content Security Policy to block. The documentation site documents it at `/components/card-grid` with a live demo
- Osirion.Blazor.Core: `HeroSection` takes `Eyebrow`, a short plain-text label above the title; `Highlights`, short phrases behind check marks under the summary, rendered through `OsirionChecklist` with empty phrases left out; and `FrameImage`, which puts the side image in a browser-like frame (a decorative bar with three dots, a border and a deeper shadow) for a product screenshot. A hero that sets none of them renders the markup it rendered before
- Osirion.Blazor.Core: `OsirionBaseSection` takes `Eyebrow`, a short plain-text label above the heading, and `Variant`, its band: `Default`, `Tinted` (`--osirion-background-secondary`) or `Dark`, which writes `data-theme="dark"` (`data-bs-theme` under Bootstrap) on the section so everything inside it takes the dark theme's tokens; an explicit `Theme` and `BackgroundColor` still win. Under a palette other than Osirion the dark band takes the Osirion dark tokens, because palettes set theirs on the root element only. A section that sets neither renders the markup it rendered before
- Osirion.Blazor.Core: `OsirionChecklist`, short phrases behind check marks, each with an optional line of description (`ChecklistItem` in `Osirion.Blazor.Core.Models`), under an optional heading at `HeadingLevel` (`3` by default; a value outside `1` to `6` moves to the nearest level). It renders a `ul` with `role="list"`, named by the heading through `aria-labelledby` and a generated id; the check marks are `aria-hidden`, and with nothing to show it renders nothing. It needs no script, and its colors come from `--osirion-*` tokens, so it follows the light and dark themes and every palette. The documentation site documents it at `/components/checklist` with a live demo
- Osirion.Blazor.Cms.Web: language versions for search engines on a site with locale routing (`IOsirionLocalePaths`). `/sitemap.xml` from `MapOsirionFeeds` declares `xmlns:xhtml` and lists each `AdditionalSitemapUrls` path in every configured culture (through `Localize`, so `/contact` and `/sr/contact`), each content item at its address in its own culture, and on every `url` with other versions one `<xhtml:link rel="alternate" hreflang="...">` per version (the culture name, itself included) plus `x-default` with the default culture's address, in Google's sitemap format; items with the same `ContentId` are each other's alternates, a culture without a translation and a `noindex` translation are not linked, an absolute additional URL is listed once without alternates, and an item whose locale is not a configured culture keeps its address. `SeoMetadataRenderer` writes the same `hreflang` links in the head when the page passes no `AlternateLanguageUrls`: a content item links its canonical address and its published translations, read through `IContentProviderManager` after the other tags (a failed read writes no links and logs a warning), and any other page links its canonical path in every culture, keeping the canonical query parameters; a page without `Locale` takes its language from the address's prefix. An `AlternateLanguageUrls` list, even an empty one, always wins. Without locale routing the sitemap is the same document byte for byte and the head is unchanged
- Osirion.Blazor.Cms.Web: `SeoMetadataRenderer` writes the whole head of a page that is not a content item, such as a contact page written in Razor, from the new `Title`, `Description`, `ImageUrl` and `CanonicalPath` parameters: the title as `{Title} | {site name}`, the description, the canonical URL (`CanonicalPath` as a path on the site or an absolute http(s) address; anything else is ignored with a logged warning), Open Graph with `og:type` `website`, Twitter tags, a schema.org `WebPage` (or the `ContactPage` or `AboutPage` that `SchemaTypes` or `FallbackSchemaType` names) and the `hreflang` links, with no author, dates or article tags. Blazor renders only the last `HeadContent` of a page, so the page keeps every head tag in this one renderer. The parameters are flat like `CollectionTitle` and `CollectionDescription`, and are ignored when `Content` or `ContentItems` is set, so existing pages render as before
- Osirion.Blazor.Core: `OsirionContactForm` and `OsirionStaticContactForm` take `AdditionalFields`, questions of the site's own after the message, so a qualification or quote form needs no form of its own. Each of up to 20 `ContactFormField` definitions has a `Name` (a letter, then up to 49 letters, digits, underscores or hyphens, unique in the form), a `Label`, a `Type` (`Text`, `MultilineText`, `Number`, `Email`, `Phone`, `Select`, `Radio` or `Checkboxes`), `Required`, `MaxLength`, `Min` and `Max` for numbers, `Options` (`ContactFormFieldOption`, a value and an optional label) and an optional `Placeholder` and `HelpText`; an invalid definition, a repeated name or a 21st field throws an `ArgumentException` naming it. The fields render in list order with a `label` (a `fieldset` and `legend` for radio buttons and checkboxes), the native `required`, `maxlength`, `min` and `max`, and their help text and error linked with `aria-describedby`. `OsirionContactForm` checks every submitted value on the server before anything is sent, together with the standard fields (required, length, a single line, number format and range, email, phone characters, one of the options, and at most 10,000 characters for all answers), shows each failure under its field with `aria-invalid`, ignores values posted under any other name, and hands the answers to `OnSubmit` as `ContactFormModel.AdditionalFieldValues` in definition order; the built-in email lists them under "Additional details", labelled and HTML-encoded, and never in a header. `OsirionStaticContactForm` posts them as `fields`, an object keyed by name (a string per field, an array for `Checkboxes`); the browser applies native constraint validation only, so the endpoint must check them again, as the documentation's Worker outline shows. Without `AdditionalFields` both forms render the same markup, post the same data and send the same email as before
- Osirion.Blazor: a site version can be derived from another by transliteration, its shell and its resource strings as well as its content. An `Osirion:Site:Locales` entry such as `"sr-Latn": { "DerivedFrom": "sr", "Transliteration": "serbian-cyrillic-to-latin" }` is the source culture's version with every text transliterated (name, menu, call to action and its footer section, announcement, footer, legal and social link texts, labels, and the copyright as markup) and its links to the source culture's pages moved to the derived culture; a key the entry writes itself wins. Startup fails, naming the key, for a source that is not a culture, is the entry's own culture, has neither an entry nor an `Osirion:Localization` culture, or is itself derived (no chains or cycles), for an unknown transliterator, and, with `Osirion:Localization` registered, for a derived culture it does not serve. `AddOsirionDerivedResourceLocalization()` wraps the registered `IStringLocalizerFactory` so a derived culture gets the source culture's string transliterated outside its placeholders (`{0}` and `{1:N0}` stay), unless the resource has its own value for it; a site that does not call it is not changed. Derived content links now take the prefix `Osirion:Localization` gives the derived culture (`/sr/contact` becomes `/sr-latn/contact`, not `/sr-Latn/contact`, which answered with a redirect), through `DerivedLocaleLinks` and `HtmlTransliteration`, now in Osirion.Blazor.Core so content and the shell share one rule
- Osirion.Blazor.Core, Osirion.Blazor.Cms.Domain and Osirion.Blazor.Cms.Infrastructure: a content locale can be derived from another by transliteration, so a site writes Serbian once in Cyrillic and serves it in Latin script too. A provider's `DerivedLocales` (FileSystem and GitHub alike) lists each one as `Locale`, `From` and `Transliteration`, for example `{ "Locale": "sr-Latn", "From": "sr", "Transliteration": "serbian-cyrillic-to-latin" }`; the derived locale is added to the effective `SupportedLocales`, so a folder written for it is recognised. When content loads, every `From` item without an item of the same localization id in the derived locale gets a derived item; a real file always wins. It keeps the localization id, slug and address, takes the path a file of that locale would have, and is marked with the new `ContentItem.DerivedFromLocale` and `IsDerived`. Its title, description, categories, tags, series and SEO texts are transliterated, and its HTML too: text and the `alt`, `title`, `aria-label` and `placeholder` attributes change, while `code`, `pre`, `kbd`, `samp`, `script`, `style`, elements with `translate="no"`, autolinks, external, `mailto:`, `tel:`, fragment and file links stay, and links to the site's own pages under the source locale move under the derived one. A derived item has no markdown source and is read only: the repositories refuse to save or delete it. Startup fails, naming the key (such as `DerivedLocales[0].From`), for a locale that is not a culture name, a `From` outside `SupportedLocales`, an unknown transliterator or a locale derived twice. `ITextTransliterator` and `TextTransliterators` (registered by `AddOsirionTransliteration`) let a site add its own transliterator; the built-in `serbian-cyrillic-to-latin` writes Љ, Њ and Џ as `LJ`, `NJ` and `DŽ` in a word in capitals and as `Lj`, `Nj` and `Dž` otherwise. Without `DerivedLocales` nothing changes
- Osirion.Blazor.Core and Osirion.Blazor: locale routing for a site with language versions, where the first segment of the address alone decides the culture of a request (`/contact` in the default culture, `/sr/contact` in Serbian), so one address always answers with the same page for caches and crawlers; no cookie and no `Accept-Language` header is read. `Osirion:Localization` (`OsirionLocalizationOptions`) sets `DefaultCulture`, served at the root without a prefix, and `Cultures`, each with a `Name`, a `Prefix` (the name in lower case by default, so `sr-Latn` gives `sr-latn`) and a `DisplayName` (the culture's native name, capitalized, by default); the default culture is added first when it is not listed. `AddOsirion(configuration)` registers it when the section exists, as do `services.AddOsirionLocalization(configuration)`, `AddOsirionLocalization(options => ...)` and the builder's `UseLocalization`, and startup fails with a message naming the key for a missing `DefaultCulture`, a name that is not a culture, a culture listed twice, two cultures with one prefix, or a prefix that is not lower-case letters and digits in words joined by hyphens. `app.UseOsirionLocalization()`, placed after `UseExceptionHandler` and `UseStatusCodePagesWithReExecute` and before `MapRazorComponents`, runs ASP.NET Core request localization with `OsirionPathRequestCultureProvider` as its only provider (it reads the original address of a re-executed error or not-found page, so that page speaks the language of the address asked for) and writes `Content-Language`; before that it answers GET and HEAD requests for a prefix in another letter case (`/SR/contact`) or for the default culture's prefix (`/en/contact`) with a 301 to the canonical address, keeping the path base and the query string and collapsing slashes and backslashes after the prefix so the target never names another host. The path is not rewritten: pages declare their localized routes (`@page "/contact"` and `@page "/sr/contact"`). `IOsirionLocalePaths` lists the cultures and reads, adds, replaces and removes the prefix of site paths (`TryGetCulture`, `Localize`, `WithoutLocale`, and `LocalizeForCurrentCulture`, which falls back through parent cultures to a configured one), keeping the query string and fragment and returning absolute, protocol-relative, `mailto:` and `tel:` links unchanged. `Osirion:Site:Locales` still decides what `OsirionSiteLayout` says in the culture a request gets. The new guide `/docs/locale-routing` shows the configuration, the middleware order, localized routes and links, and the `HtmlEncoder` a site in a non-Latin script should register
- Osirion.Blazor.Navigation: `OsirionLanguagePicker` links the current page in each of the site's languages, from `IOsirionLocalePaths`: a `nav` (`osirion-language-picker`, named by `AriaLabel`, `Language` by default) with a list of plain links, each with `hreflang` and `lang` set to the culture name and the language's `DisplayName` as its text, the culture of the address marked with `aria-current="true"`, the query string kept and the default culture's link without a prefix. It renders under static SSR without a script, follows navigation under interactive rendering, writes its links from the application's path base and never from the request's host, renders nothing for a site with fewer than two cultures, and is styled through `--osirion-*` tokens with its own `--osirion-language-picker-*` hooks
- Osirion.Blazor.Cms.Web: `SeoMetadataRenderer` takes `Locale`, the language of a list page (`ContentItems`), which had no way to name one and always wrote `og:locale` `en_US` and the language meta tags as `en`. A page with `Content` keeps taking its language from the item
- Osirion.Blazor: `OsirionSiteLayout` speaks the language of the request. `Osirion:Site:Labels` (`SiteLabels`) holds the shell's own texts, which were English and could not be changed: the skip link (`SkipLink`), the names of the menu and its toggle (`Menu`, `MenuToggle`), the theme toggle (`SwitchToDarkTheme`, `SwitchToLightTheme`), the search box (`Search`, the field's label and the button's text, and `SubmitSearch`, the button's name), the footer's legal links (`LegalLinks`) and the announcement (`Announcement`, `DismissAnnouncement`). Each defaults to the English text the component used before, so a site that sets none renders as before. `Osirion:Site:Locales` holds what each language version says differently, keyed by culture name (`sr-Latn-RS`, `en`, in any letter case): `Name`, `LogoUrl`, `HomeUrl`, `Menu`, `SearchUrl`, `SearchPlaceholder`, `CallToAction`, `Announcement`, the footer's values and `Labels`. The layout uses the entry of `CultureInfo.CurrentUICulture`, which `UseRequestLocalization` sets, or of its nearest parent culture (`sr-Latn`, then `sr`); a value the entry sets replaces the site's as a whole, and one it leaves out is the site's. `OsirionSiteOptions.ForCulture(culture)` returns that view for code. Startup fails, naming the key, for a locale key that is not a culture name and for a problem in a value a locale sets, such as a call to action whose `FooterSection` names none of the sections that version shows
- Osirion.Blazor.Theming: `ThemeToggle` takes `SwitchToDarkLabel` and `SwitchToLightLabel`, what the button says while the light or the dark theme is on, and writes both on the button (`data-switch-to-dark-label`, `data-switch-to-light-label`), so `theme-toggle.js` names the button in the page's language after a switch instead of writing English
- Osirion.Blazor.Cms.Web: `SearchBox` takes `SubmitLabel`, the submit button's accessible name, which was always "Submit search"
- Osirion.Blazor.Core: `OsirionFooter` takes `BottomLinksLabel`, the accessible name of the `nav` around `BottomLinks`, which was always "Footer legal navigation"
- Osirion.Blazor.Core: `OsirionStaticContactForm` takes the layout parameters of `OsirionContactForm`: `FormTitle` and `FormDescription` (a heading and a paragraph above the form), `ContactInfo`, `ShowContactInformation` and `ContactInfoTitle` (an `OsirionContactInfoSection` in a shaded panel beside the form, below it under 768px), `SideBySideLayout` (`false` keeps the panel below the form at every width), an optional subject field (`ShowSubjectField`, `SubjectLabel`; sent as `subject`, at most 200 characters) and the placeholders `NamePlaceholder`, `EmailPlaceholder`, `SubjectPlaceholder` and `MessagePlaceholder`. `ContactInformation.AdditionalItems` is a list of `ContactInfoItem` (`Label`, `Text`, an optional `Href` that must pass `SafeLink.IsSafe`, and an optional `ContactInfoIcon`: `Address`, `Phone`, `Email`, `Website`, `Calendar`, `Clock` or `Link`) that `OsirionContactInfoSection` draws as extra rows after the website row, for a booking link, a social profile, working hours or a reply time; `OsirionContactForm` and `ContactPage` show them too. Used with none of the new parameters, both components render the same markup as before, and the form posts the same JSON (`subject` only when the field is shown)
- Osirion.Blazor.Core: `OsirionCallToActionSection`, the closing call to action of a page, so a site no longer writes its own markup for it: a heading at `HeadingLevel` (`2` by default; a value outside `1` to `6` moves to the nearest level), a `Description` paragraph, `ChildContent`, and up to two plain links styled as buttons (`PrimaryButtonText` and `PrimaryButtonUrl`, `SecondaryButtonText` and `SecondaryButtonUrl`). The `<section>` is named by its heading through `aria-labelledby` and a generated id; a button is rendered only with a label and a safe URL (a path on the site, or an http, https or mailto address; `javascript:` and protocol-relative URLs leave it out), and takes the CSS framework's primary or secondary button class; with nothing to show the component renders nothing. It needs no script, and its panel uses only `--osirion-*` tokens, so it follows the light and dark themes and every palette. getosirion.com documents it at `/components/call-to-action-section` with a live demo
- Osirion.Blazor.Navigation: `Menu` has a `PinnedActions` slot for content that stays in the bar at every width, such as a site's main call to action. A horizontal bar shows it after `Actions`, and below the collapse breakpoint it stays in the bar, drawn after the toggle, instead of moving into the drawer, where `Actions` goes. It renders once, in a `div` with the class `osirion-menu-pinned-actions` after the drawer in keyboard order, so a screen reader meets the link once; a menu without it renders no new element.
- Osirion.Blazor: `SiteCallToAction.FooterSection` (`Osirion:Site:CallToAction:FooterSection`) names a footer section by its `Title`, and the call to action becomes the last link of that column, so a footer offers "Book a call" without repeating the button's address in `FooterSections`. `GetErrors` rejects a title that matches no section (compared exactly, letter case included), so startup names the key instead of the link silently missing.
- Docs: every page of getosirion.com has its own link preview card (1200 x 630, the page title and section on the site's dark theme) instead of one shared placeholder, and the templates, getting started, themes and four blog posts show screenshots, with their width and height so the page does not shift. Cards and screenshots are served from `media.getosirion.com` (R2, cached for a year) and are rebuilt from `tools/site-media` (`inventory.py`, `cards.mjs`, `shots.mjs`, `optimize.py`). The site's cookie banner says what it asks for instead of the library's default text, which implied consent by browsing on
- Osirion.Blazor.Core: `OsirionStaticContactForm`, a contact form for sites published as static files (for example on Cloudflare Workers static assets), where no ASP.NET server receives a form post. Its script posts the message as JSON (`name`, `email`, optional `company`, `message`, the honeypot `website` and the Cloudflare Turnstile `token`) to an `Endpoint` the site provides, such as a Cloudflare Worker, and shows the answer (`{"ok": true}` or `{"ok": false, "error": "fields" | "check" | "failed"}`) as a message in a `role="status"` region. The form renders hidden and its script reveals it, so visitors without script see `NoScriptContent` instead of a form that cannot send. The endpoint must be a path on the site or an `https` URL, and the component writes no inline script or event handler, so a strict Content Security Policy only has to add `https://challenges.cloudflare.com` to `script-src` and `frame-src`. `OsirionContactForm`, which posts to the server, is unchanged
- Osirion.Blazor.Cms.Domain, Osirion.Blazor.Cms.Infrastructure and Osirion.Blazor.Cms.Web: content providers report their locales through the new `ILocalizationInfoProvider.GetLocalizationInfoAsync`, which `ContentProviderBase` implements for the FileSystem and GitHub providers from the content already loaded: the default locale, then each of `SupportedLocales` that has published content, with English and native names (only the default locale while `EnableLocalization` is off). `LocalizedNavigation` uses it to render its locale selector, links to the current page in each locale named by `LocaleNameFormatter` (the native name by default), with `aria-current` on the current locale and a new `LocaleUrlFormatter` for other routes; `OnLocaleChanged` runs in interactive render modes
- Osirion.Blazor.Cms.Web: `AboutPage` takes a `HeaderContent` (`RenderFragment<ContentItem>`), the page's own header above the body in place of the heading or the hero, as on `ArticlePage`, so a site can put a call to action such as a booking button at the top of its about page. Its header (or default heading), body and child content are centered at the new `--osirion-about-page-width` custom property, which defaults to `--osirion-container-lg` (960px when unset), so a site can change the page's width without changing the other components that read the container token
- Osirion.Blazor.Cms.Web: `ArticlePage` takes a `FooterContent` (`RenderFragment<ContentItem>`), rendered after the article and its sidebar in `footer.osirion-article-page-footer`, outside the article column, for a closing call to action or related links that do not belong in the article itself
- Osirion.Blazor.Cms.Web: `ContentListPage` takes a `HeaderContent` (`RenderFragment`), the page's own header above the list in place of the list's title and description, for example the title with a strip of series links above the posts; `Title` and `Description` still name the page in its head metadata. Unused, none of the new slots changes the rendered markup
- Osirion.Blazor and Osirion.Blazor.Core: `OsirionSiteLayout` renders a call to action button in the menu from `Osirion:Site:CallToAction` (`Text` and `Href`, for example "Book a call" linking to a scheduling page), so a site gets one from `appsettings.json` instead of replacing the whole `Header`. It is a link styled as the primary button of the CSS framework (`btn btn-primary` under Bootstrap), after the search box and theme toggle and before `MenuActions`; below 1200px it shows in the opened menu on a row of its own. An `http` or `https` address gets `rel="noopener"` and opens in the same tab. Startup fails, naming the key, when `Text` or `Href` is missing or `Href` is neither a path on the site nor an `http`, `https` or `mailto` address, and options configured without that check render no button for such a value. Without the key the menu renders as before. The layout uses two helpers of `Osirion.Blazor.Core.Utils` that are now public, so markup outside `OsirionComponentBase` applies the same rules as the components: `SafeLink.IsSafe`, the link check behind `OsirionAuthorCard` and `OsirionPricingTable`, and `ButtonClasses.Primary`, the primary button classes of each CSS framework
- Osirion.Blazor.Core and Osirion.Blazor.Cms.Web: `OsirionContentNotFound` and `ContentPage` take a `HeadingLevel` parameter, `1` to `6` like `ContentView`, so a page that embeds them keeps a single `h1`. It defaults to `1`, which changes nothing for existing pages; a value outside the range moves to the nearest level, and the title keeps its look. The getosirion.com demos on `/components/content-not-found` and `/components/content-page` set `2`, so those pages no longer have two `h1` elements
- Osirion.Blazor.Cms.Web: `SeoMetadataOptions.ReferrerPolicy` (`Osirion:Seo:ReferrerPolicy`) and the `ReferrerPolicy` parameter of `SeoMetadataRenderer` write `<meta name="referrer">` with a policy of the Referrer Policy specification (`no-referrer`, `no-referrer-when-downgrade`, `same-origin`, `origin`, `strict-origin`, `origin-when-cross-origin`, `strict-origin-when-cross-origin` or `unsafe-url`, in any letter case), for a host that cannot send a `Referrer-Policy` header. Without one no tag is written; another value writes nothing and logs a warning
- Osirion.Blazor.Core, Osirion.Blazor.Analytics and Osirion.Blazor: cookie consent can be evaluated in the browser, for sites exported to static files. ### Security
- Osirion.Blazor.Cms.Admin: every routed admin page (`/osirion`, `/osirion/dashboard`, `/osirion/content`, `/osirion/content/edit`, `/osirion/settings`, `/osirion/login`) requires the authorization policy `"Osirion.Cms.Admin"` (`CmsAdminAuthorization.PolicyName`).
